# ADR-0017: Wallet adapters in the gateway

Status: accepted · 2026-10-17

## Context

One-tap purchases complete a passkey-approved purchase with the developer's own wallet, first their Shop account, instead of handing the buyer off to the merchant's checkout. Shop's terms allow personal agents on a shopper's own account, not a platform acting for many shoppers, so the call has to come from the developer's own gateway, with their own token. Until now the gateway reached one outside system and held no merchant-facing integration.

Shop is a hard destination to hold to the invariants:

- Its answers carry the buyer's identity. `get_account` returns the name, email, phone, saved addresses and order history; a checkout echoes the delivery address; its payment instrument may carry a billing address; error messages can quote any of these (invariant 3).
- Its requests carry credentials: a bearer token in a header, a Shop Pay token inside the payment instrument, and the refresh token at revocation (invariant 2, ADR-0014).
- Shop's skill tells agents to copy a saved address, fields included, into the checkout. Forwarding a postal address would break invariant 3 (plan kill criterion K4).
- Shop speaks MCP 2026-07-28 statelessly: there is no `initialize`, and every request carries an `Mcp-Method` header and a `params._meta` block.

## Decision

- **A wallet adapter is the developer's own payment rail, not a merchant integration.** The gateway may hold wallet adapters behind the rail-agnostic port in `src/wallet` (`WalletAdapter`). The gateway still holds no merchant integration. The first adapter is `src/wallet-shop`, with a fake Shop in `src/wallet-shop-fake` (MCP server and revocation on 127.0.0.1, with fault switches for every attack case). Only `src/disclosure` may import the adapter, and it builds it with `connectShop`, so every send to Shop goes through the disclosure core.
- **Our own MCP client, not the SDK.** `src/wallet-shop/rpc.ts` builds each JSON-RPC `tools/call` itself over `node:http(s)`: fresh connection, 30 s timeout, 1 MiB answer cap. Each request carries `Mcp-Method`, `Mcp-Name`, `Mcp-Protocol-Version: 2026-07-28` and `params._meta` (protocol version, client capabilities, client name). The identity check lets the client name through at exactly `params._meta["io.modelcontextprotocol/clientInfo"].name`, and only when it is exactly `intent-gateway`, as it lets the tool name through at `params.name`. A request with more than one `content-type` header is refused, since the body is read by it.
- **A fixed tool allow-list.** The adapter calls only `get_account`, `create_checkout`, `complete_checkout`, `get_checkout` and `search_orders`, plus revocation on Shop's account server. Any other tool Shop advertises, a spend-request tool included, is refused before anything is logged. `update_checkout` is not on the list: delivery is set by id in `create_checkout` itself. If Shop turns out not to accept a destination there (open until the S1 spike), adding `update_checkout` is a change to this decision, not a code-only fix.
- **Delivery by saved-address id only.** The adapter reads the saved-address id from `get_account` (an opaque `gid://shopify/<Type>/<digits>` with no query suffix: a query could carry a token, which the log would keep in clear under `id`, or address text; if S1 shows Shop's ids carry one, allowing it is a change to this decision) and sends `destinations: [{id, type: "shipping_address"}]`. With no such id it throws `AddressFieldsRequiredError` and sends no `create_checkout`; an answer that asks for address fields throws the same and is never retried with fields. `complete_checkout` forwards the payment instrument exactly as Shop offered it, so an instrument that carries a billing address, or anything else `findIdentity` flags, is refused before the send (`AddressFieldsRequiredError("payment")`). The adapter does not strip it and try again: whether Shop needs it is open (K4), and a money path does not improvise.
- **Allow-list projection of every answer, errors included.** Only the budget left, the checkout's sha256 reference, its status, lines `{variant_ref, quantity, title}`, the store domain, the merchant origin, the total and the order id come out. The ship-to ZIP is compared in memory against the signed snapshot's and only `match | differs | unknown` is kept. From an error only the HTTP status, the JSON-RPC numeric code and a fixed local label are kept; Shop's message never reaches a tool result, stderr or the chain. Shop's answers are logged, as for every wallet, only as a status, a sha256 and a size (ADR-0014).
- **Store identity as Shop reports it.** Shop names a store by its `*.myshopify.com` domain, which is not the storefront origin an offer shows. The adapter records the domain Shop reports (`storeDomain`) beside the merchant origin, and never compares the two; that binding check belongs to the completion step and is open.
- **A checkout id is a secret value.** A UCP checkout id can carry a credential in its query (`gid://shopify/Checkout/<token>?key=<secret>`, seen on a Shopify store), and Shop's may too. The adapter therefore:
  - names a checkout everywhere outside itself by `checkoutRef`, the contract's checkout ref hash: `"sha256:" + hex(SHA-256(utf8(p)))` of the part `p` of the id before its first `?` (amendment L1, as amended by ADR-0019), never the id. **Rule for the completion step:** the `checkout_ref` it chains (binding check 2) is this value;
  - holds the id itself in memory, for the next call to Shop, and (ADR-0019) sealed in the encrypted checkout vault, so a restarted gateway can still read a checkout it may have completed;
  - digests the id in every logged request (`params.arguments.id` is a secret path of the `shop` destination); answers are logged as a digest anyway;
  - keeps no other id that has a query: variant and order references must be plain (`gid://shopify/<Type>/<digits>`-like, no `?`), or they are dropped.
- **Idempotency keys are UUID v4** (Shop's schema: `format: uuid`). The adapter refuses any other key, for `create_checkout` and `complete_checkout` alike.
- **Revocation is a disclosed send.** `intent wallet unlink shop` first posts the refresh token (else the access token) to Shop's RFC 7009 endpoint, `POST <auth>/oauth/revoke`, with `client_id` and no client secret, through the disclosure core (destination `shop_accounts`), then deletes the vault file whatever the answer. The `wallet` entry says `revoked: true` only when Shop answered HTTP 200; otherwise `revoked: false` and the output names the Shop setting to revoke by hand.
- **The disclosure core reads form bodies.** OAuth endpoints take `application/x-www-form-urlencoded`. The core and `intent verify` read such a body as `{name: value}` by its logged `content-type`, scan it, digest its secret values and log it re-written by `URLSearchParams`. A form with a repeated name, or other escapes, cannot be logged as sent and is refused, as a non-canonical JSON body is.
- **Compound token names are secret keys** (amends ADR-0014). Besides the listed keys, every key whose last word is `token` or `bearer` (`session_token`, `authToken`, `bearer`) is digested in the log, and `intent verify` fails a disclosure that holds one in clear. `token_type_hint` (last word `hint`) stays readable.
- **No built-in Shop client.** Shop's public device-flow client is for a shopper's own agent; a gateway shipped to others needs its own registered client, which does not exist yet. `INTENT_SHOP_CLIENT_ID` (a client id or the https URL of a client-ID metadata document) has no default; without it `intent wallet status` says one-tap with Shop is unavailable and purchases are handed off.
- **`DisclosureRefusedError` reads as "not sent".** A request the core refuses for a logging rule becomes a `blocked` tool result naming the rule, and a one-line CLI error, as `DisclosureBlockedError` does.

## Consequences

The gateway now reaches two outside systems; `CLAUDE.md` lists the wallet among the adapters, each with its fake. The Shop field names followed Shop's published schemas as of 2026-10-16; the S1 spike (2026-10-18) replaced the guesses with what Shop returned (amendment below). The fake Shop answers with the captured shapes, filled with made-up data; the captured answers themselves are not committed, since they are a real buyer's (redacted, but not published).

A wider secret-key rule digests more values in the log, among them any field named like `next_page_token`; such a value is still checkable by its sha256. A chain written before this change that holds such a key in clear now fails `intent verify`; the requests the gateway builds for its public API host carry no such key. The completion step (who calls `complete_checkout`, once, and how a lost answer is reconciled) is not part of this decision: it comes with the completion step machine.

## Amendment: the out-of-band check (2026-10-17, plan G12)

`search_orders` was already on the tool allow-list; this amendment says what the gateway does with it. The allow-list itself is unchanged.

- **On demand only.** `intent wallet check shop [--since 7d]` sends one `search_orders` request, `{pagination: {limit: 50}}`, through the disclosure core like every Shop call. Nothing polls in the background. No cursor from an answer is ever sent back, so the check covers one page; when Shop says more exist (or returns a full page) the result is marked `complete: false`. Whether `search_orders` takes a date filter waits for the S1 spike; the period is applied to the projected creation times.
- **Projection of an order.** Each order comes out as `{order_ref, total, merchant_origin, created_at}` only (`projectOrders`). An order whose id is not a plain reference (a query, identity text) is dropped whole. The buyer's name, email, phone, shipping and billing addresses, line titles and notes are never read.
- **Matching against the chain.** An order is matched when an `outcome` entry names its `order_ref`; any other order in the period is unmatched. The output says what Shop reported and what the chain names, never how an unmatched order was placed (invariant 5).
- **What is chained.** `wallet {rail, action: "checked", since, order_count, unmatched_count, unmatched_total_minor, complete}`: counts and a USD total, no order reference. `intent verify` holds a `checked` entry to exactly these keys, as it holds `linked` and `unlinked` to `{rail, action, revoked}`. The unmatched orders' references, totals and origins are printed to the developer only.

## Amendment: aligned with the S1 spike (2026-10-18)

The S1 spike linked a real Shop account with the public device-flow client and placed one real order. Where Shop differed from the decision above, the adapter now follows Shop:

- **No address and no address id.** With the lines alone (no `fulfillment`, no `buyer`), `create_checkout` came back with the buyer's preferred saved address filled in under a new destination id, status `ready_for_complete`. The adapter now sends `{shop, checkout: {line_items}, meta: {idempotency-key}}` only, and reads no address id from `get_account` (Shop's ids turned out to be UUIDs, not gids). An answer that asks for address fields still throws `AddressFieldsRequiredError` and is never retried with fields: the K4 regression tests stay. Choosing a non-preferred address is untested and not offered.
- **Pay with the agent budget only.** A checkout offered two instruments, both `handler_id: shop_pay`: the Shop Pay card (`type: shop_pay`, `selected: false`) and the agent budget (`type: delegated_budget`, id `shop_…`, `selected: true`). Paid from the budget, Shop showed no prompt of its own. `complete_checkout` now sends exactly the one `delegated_budget` instrument as offered, plus `selected: true`; with none, or more than one, offered it throws `CompletionRefusedError` (`no_budget_instrument`) and sends nothing. The card is never sent. `WalletCheckout.budgetOffered` says whether a quote can be paid this way.
- **Budget shape.** `get_account` shows the budget as a `payment.instruments[]` entry with `display {limit, remaining_amount, renewal_type, renews_at}` (integer minor units) and a top-level `currency`; no budget is an empty list. Only `remaining_amount` and `currency` are kept. None, several, or an odd value is `null`: unknown.
- **A removed connection.** Revoking tokens does not remove the connection from the Shop app. When the buyer removes it there, the token still answers `get_account`, with the warnings `claims_unavailable`, `addresses_unavailable`, `budget_unavailable` and `payment_instruments_unavailable` and no data. Any of them makes `WalletAccount.connected` false; `intent wallet status` reads the account once (a logged send) and says the wallet is not linked at Shop.
- **Identity and credentials in answers, whatever the scope.** Under `openid personal_agent` (no `email`), `get_account` still returned the buyer's email, picture URL, names, full addresses with phone, the card's last digits and holder name, and `credential {type, token}` per card; checkouts echo the buyer's email and phone and the full delivery address. The projection's allow-list already dropped them; the fake now returns all of them, so the tests prove none reaches the chain or a result. The instrument's `credential` is a secret path when sent back.
- **Revocation of both tokens.** Revoking the refresh token answered 200 with an empty body, and the access token kept working. `revoke()` now posts the refresh token, then the access token; `revoked: true` only when Shop answered 200 to both. The CLI then tells the developer to remove the connection in the Shop app.
- **Token refresh.** The token answer had `access_token`, `token_type: Bearer`, `expires_in: 3600`, a `refresh_token`, `scope` and `access_type` (ignored), and no `id_token`. The vault now keeps `expires_at`. An access token within 60 s of expiry, or one Shop answers 401 to, is refreshed by a `refresh_token` grant through the disclosure core (destination `shop_accounts`, the refresh token digested); the new tokens go to the vault. Only a read is sent again after a refresh; `create_checkout` and `complete_checkout` never are. A refused refresh is a 401 saying to link again.
- **Error shapes.** A tool error is HTTP 200 with `isError: true`, `ucp.status: "error"` and `messages[{type, code, severity}]`; the adapter keeps the code token (`WalletRailError.railCode`, e.g. `checkout_completion_ineligible`) and never the message. A schema error or an unknown tool is HTTP 400 with JSON-RPC -32602, read as an error with its code; a bad token is 401.
- **Idempotency.** `create_checkout` replayed with the same key returned a new checkout. The adapter sends it once per call; a send that may have reached Shop with no usable answer throws `CheckoutUnconfirmedError` (ADR-0019 then never creates again for that purchase).
- **Order search.** An order's `id` is Shop's own UUID; `shopify_order_id` holds the digits of the `gid://shopify/Order/<digits>` a completed checkout returns, and `seller` has `domain` (the storefront) and `myshopify_domain`. `checkout_id` is an order-status URL with a credential in its query, not the checkout gid, and is never read. `projectOrders` now builds the order ref from `shopify_order_id` (not scanned as a card: it is built from digits), takes the merchant origin from `seller.domain`, and the time from `placed_at`.
- **Store identity.** A checkout carries no merchant field; the store is the `shop` the gateway named, and a completed order's `permalink_url` is on the myshopify domain, which the projection reports as `storeDomain`. The storefront's primary domain appears only inside a payment handler's config, which is not read. How check 1 binds the store is ADR-0019's amendment.

## Amendment: the gateway's own Shop client by default (2026-10-18)

Replaces the "No built-in Shop client" point above.

- **Our client file by default.** Without `INTENT_SHOP_CLIENT_ID`, `intent wallet link shop` and `intent init` sign in as the gateway's own client, the client-ID metadata document at `https://gateway.intentai.shop/shop-client.json`: its `client_id` is that URL, a public client (`token_endpoint_auth_method: none`) with the device-code and refresh grants and scope `openid personal_agent`. The constant is `DEFAULT_SHOP_CLIENT_ID` in `src/wallet-shop`, beside Shop's other defaults; `src/config` keeps `shopClientId` null until the variable is set.
- **Another client only when named.** `INTENT_SHOP_CLIENT_ID` replaces the default, for example with Shop's public client for the developer's own agent. The gateway never falls back to another client by itself: when Shop answers `invalid_client`, the link ends with one line saying which client was refused, naming `INTENT_SHOP_CLIENT_ID` as the explicit opt-in (or, when that set the client, saying to check it), and nothing more is sent.
- **A wallet keeps its client.** A linked wallet keeps the client it was linked with, in its vault, for every Shop call, refresh and revocation, so a gateway started without `INTENT_SHOP_CLIENT_ID` (the `claude mcp add` line sets only `INTENT_CLOUD_URL`) still uses it. If `INTENT_SHOP_CLIENT_ID` later names another client, the gateway says so in one line and keeps the linked one; only `intent wallet link shop` again changes it. A vault from before the client was kept in it uses `INTENT_SHOP_CLIENT_ID` when set, else the gateway's own client, and records it at the next refresh.
- **Unchanged.** The scope, the device flow, and every log-before-send rule: the client id is logged in each device and token request before it leaves, as before. `intent wallet status`, `check` and `serve` no longer report one tap unavailable for want of a client.

Step 2b (2026-10-18) settled it for now: Shop's authorization server never fetched the client file and answered 401 `invalid_client`. A formal registration is pending. Until it lands, a developer links their own account by setting `INTENT_SHOP_CLIENT_ID` to a client Shop accepts, such as Shop's public client for their own agent; that is never the gateway's default. The Claude Code onboarding prompt sets it on its `intent` command line, so a developer who follows it links their own account, for their own use, as Shop's public client (the connection shows in the Shop app as Personal Agent); the registered client replaces it there when it exists.
