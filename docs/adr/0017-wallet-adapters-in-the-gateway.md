# ADR-0017: Wallet adapters in the gateway

Status: accepted · 2026-10-17

## Context

One-tap purchases complete a passkey-approved purchase with the developer's own wallet, first their Shop account, instead of handing the buyer off to the merchant's checkout. Shop's terms allow personal agents on a shopper's own account, not a platform acting for many shoppers, so the call has to come from the developer's own gateway, with their own token. Until now the gateway reached one outside system and held no merchant-facing integration.

Shop is a hard destination to hold to the invariants:

- Its answers carry the buyer's identity. `get_account` returns the name, email, phone, saved addresses and order history; a checkout echoes the delivery address; its payment instrument may carry a billing address; error messages can quote any of these (invariant 3).
- Its requests carry credentials: a bearer token in a header, a Shop Pay token inside the payment instrument, and the refresh token at revocation (invariant 2, ADR-0014).
- Shop's skill tells agents to copy a saved address, fields included, into the checkout. Forwarding a postal address would break invariant 3 (plan kill criterion K4).
- Shop speaks MCP 2026-07-28 statelessly: there is no `initialize`, and every request carries an `Mcp-Method` header and a `params._meta` block.

## Decision

- **A wallet adapter is the developer's own payment rail, not a merchant integration.** The gateway may hold wallet adapters behind the rail-agnostic port in `src/wallet` (`WalletAdapter`). The gateway still holds no merchant integration. The first adapter is `src/wallet-shop`, with a fake Shop in `src/wallet-shop-fake` (MCP server and revocation on 127.0.0.1, with fault switches for every attack case). Only `src/disclosure` may import the adapter, and it builds it with `connectShop`, so every send to Shop goes through the disclosure core.
- **Our own MCP client, not the SDK.** `src/wallet-shop/rpc.ts` builds each JSON-RPC `tools/call` itself over `node:http(s)`: fresh connection, 30 s timeout, 1 MiB answer cap. Each request carries `Mcp-Method`, `Mcp-Name`, `Mcp-Protocol-Version: 2026-07-28` and `params._meta` (protocol version, client capabilities, client name). The identity check lets the client name through at exactly `params._meta["io.modelcontextprotocol/clientInfo"].name`, and only when it is exactly `intent-gateway`, as it lets the tool name through at `params.name`. A request with more than one `content-type` header is refused, since the body is read by it.
- **A fixed tool allow-list.** The adapter calls only `get_account`, `create_checkout`, `complete_checkout`, `get_checkout` and `search_orders`, plus revocation on Shop's account server. Any other tool Shop advertises, a spend-request tool included, is refused before anything is logged. `update_checkout` is not on the list: delivery is set by id in `create_checkout` itself. If Shop turns out not to accept a destination there (open until the S1 spike), adding `update_checkout` is a change to this decision, not a code-only fix.
- **Delivery by saved-address id only.** The adapter reads the saved-address id from `get_account` (an opaque `gid://shopify/<Type>/<digits>` with no query suffix: a query could carry a token, which the log would keep in clear under `id`, or address text; if S1 shows Shop's ids carry one, allowing it is a change to this decision) and sends `destinations: [{id, type: "shipping_address"}]`. With no such id it throws `AddressFieldsRequiredError` and sends no `create_checkout`; an answer that asks for address fields throws the same and is never retried with fields. `complete_checkout` forwards the payment instrument exactly as Shop offered it, so an instrument that carries a billing address, or anything else `findIdentity` flags, is refused before the send (`AddressFieldsRequiredError("payment")`). The adapter does not strip it and try again: whether Shop needs it is open (K4), and a money path does not improvise.
- **Allow-list projection of every answer, errors included.** Only the budget left, the checkout's sha256 reference, its status, lines `{variant_ref, quantity, title}`, the store domain, the merchant origin, the total and the order id come out. The ship-to ZIP is compared in memory against the signed snapshot's and only `match | differs | unknown` is kept. From an error only the HTTP status, the JSON-RPC numeric code and a fixed local label are kept; Shop's message never reaches a tool result, stderr or the chain. Shop's answers are logged, as for every wallet, only as a status, a sha256 and a size (ADR-0014).
- **Store identity as Shop reports it.** Shop names a store by its `*.myshopify.com` domain, which is not the storefront origin an offer shows. The adapter records the domain Shop reports (`storeDomain`) beside the merchant origin, and never compares the two; that binding check belongs to the completion step and is open.
- **A checkout id is a secret value.** A UCP checkout id can carry a credential in its query (`gid://shopify/Checkout/<token>?key=<secret>`, seen on a Shopify store), and Shop's may too. The adapter therefore:
  - names a checkout everywhere outside itself by `checkoutRef = "sha256:" + hex(SHA-256(utf8(id)))`, never the id. **Rule for the completion step:** the `checkout_ref` it chains (binding check 2) is this value;
  - holds the id itself in memory only, for the next call to Shop, so after a restart a reference reaches nothing until the completion step finds the checkout again another way;
  - digests the id in every logged request (`params.arguments.id` is a secret path of the `shop` destination); answers are logged as a digest anyway;
  - keeps no other id that has a query: variant and order references must be plain (`gid://shopify/<Type>/<digits>`-like, no `?`), or they are dropped.
- **Idempotency keys are UUID v4** (Shop's schema: `format: uuid`). The adapter refuses any other key, for `create_checkout` and `complete_checkout` alike.
- **Revocation is a disclosed send.** `intent wallet unlink shop` first posts the refresh token (else the access token) to Shop's RFC 7009 endpoint, `POST <auth>/oauth/revoke`, with `client_id` and no client secret, through the disclosure core (destination `shop_accounts`), then deletes the vault file whatever the answer. The `wallet` entry says `revoked: true` only when Shop answered HTTP 200; otherwise `revoked: false` and the output names the Shop setting to revoke by hand.
- **The disclosure core reads form bodies.** OAuth endpoints take `application/x-www-form-urlencoded`. The core and `intent verify` read such a body as `{name: value}` by its logged `content-type`, scan it, digest its secret values and log it re-written by `URLSearchParams`. A form with a repeated name, or other escapes, cannot be logged as sent and is refused, as a non-canonical JSON body is.
- **Compound token names are secret keys** (amends ADR-0014). Besides the listed keys, every key whose last word is `token` or `bearer` (`session_token`, `authToken`, `bearer`) is digested in the log, and `intent verify` fails a disclosure that holds one in clear. `token_type_hint` (last word `hint`) stays readable.
- **No built-in Shop client.** Shop's public device-flow client is for a shopper's own agent; a gateway shipped to others needs its own registered client, which does not exist yet. `INTENT_SHOP_CLIENT_ID` (a client id or the https URL of a client-ID metadata document) has no default; without it `intent wallet status` says one-tap with Shop is unavailable and purchases are handed off.
- **`DisclosureRefusedError` reads as "not sent".** A request the core refuses for a logging rule becomes a `blocked` tool result naming the rule, and a one-line CLI error, as `DisclosureBlockedError` does.

## Consequences

The gateway now reaches two outside systems; `CLAUDE.md` lists the wallet among the adapters, each with its fake. The Shop field names follow Shop's published schemas as of 2026-10-16; the budget's and the saved-address id's exact shape, and whether Shop accepts an id-only destination, wait for the S1 spike's captured answers. Until then one-tap fails closed: an unknown shape gives no budget or `AddressFieldsRequiredError`, never a send of address fields. Recorded Shop fixtures (`test/fixtures/shop/`) come with S1.

A wider secret-key rule digests more values in the log, among them any field named like `next_page_token`; such a value is still checkable by its sha256. A chain written before this change that holds such a key in clear now fails `intent verify`; the requests the gateway builds for its public API host carry no such key. The completion step (who calls `complete_checkout`, once, and how a lost answer is reconciled) is not part of this decision: it comes with the completion step machine.
