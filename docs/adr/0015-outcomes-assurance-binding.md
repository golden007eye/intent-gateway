# ADR-0015: Outcomes, assurance and binding, read by the gateway

Status: accepted · 2026-10-17

## Context

After an approval, something happens to the purchase: the buyer is handed off to the merchant, an order is placed (or not), the checkout expires, or, in a one-tap purchase, the gateway's own wallet completes it. Contract 1.6.0 (Appendix G, with its security amendment) lets Intent Cloud state that outcome, with the source that told it and the assurance it gives (`verified` or `reported`), and sign it in an outcome statement. It defines `binding-v1`, five checks of an observed order against the snapshot the passkey signed: merchant origin, checkout, line, ZIP and total. What Intent Cloud reported must never widen what the gateway does (invariant 1), and the gateway's words must never claim more than it can check (invariant 5). The gateway also needs one record of what it concluded, which `intent verify` can re-check offline.

## Decision

- **Only a verified statement is acted on (M1).** A 1.6.0 status carries `outcome` and `outcome_statement` together, with JCS-equal outcomes. The gateway acts only on a statement that verifies: an Ed25519 signature by an approval key of a verified key statement over `"intent-outcome-v1\n" || JCS(statement without cloud_signature)` (base64url, no padding), for this approval and the snapshot hash it chained, and consistent (M2): the binding result follows its checks with `ship_to_optional` from the sources table, `ordered` and `mismatch` carry `order_ref`, `final_total` and `binding`, an `ordered` total is at most the approved total, the state is one of the snapshot's mode, and the source is one whose events Intent Cloud received itself, within its assurance cap. Each refusal names its rule (`refused_by`, as in vector o2). An outcome with no statement, or a statement that does not verify, shows nothing.
- **Never more than the statement (O1, O2).** The gateway records what Intent Cloud reported as that service's report, beside its own binding result: it re-runs the result rule over the statement's checks with its own total check against the approved snapshot. It shows `ordered` only when the statement verified and its own re-run gives `ok`. A statement Intent Cloud did sign but that breaks a content rule shows only the lesser state the gateway's reading supports: an order whose total or binding result does not hold shows `mismatch`; an order whose source or assurance cannot carry one shows `reported`. The tool result's sentence is worded "Intent Cloud reported …"; when the status's own `state` disagrees with its outcome, it repeats nothing.
- **R5a.** A terminal verified outcome is final, a verified outcome replaces a reported one, and a reported outcome replaces a reported one only from the same source. A later statement that may not replace the one recorded is not adopted, and the gateway warns.
- **One `outcome` entry per distinct outcome.** `basis: "cloud"` holds what Intent Cloud reported (`{state, source, assurance}`), whether the statement verified and why not, the statement as canonical JSON (left out, and nothing shown, when it holds what looks like buyer identity), the gateway's binding re-run, the state shown, and the order it names only when something was shown. `basis: "local"` is the gateway's own verdict from evidence it holds (its precheck refusal, or Shop's checkout read), written by the one-tap completion; its binding inputs keep the checkout ref hash, never the raw checkout id.
- **`intent verify` re-checks outcomes offline.** An outcome must name an approval that verified earlier in the chain. A `cloud` entry's statement is re-verified at the entry's time against the key statement then in force, and the reading is re-run: the recorded verification, refusal, binding and shown state must be what the statement gives. A `local` entry re-runs binding-v1 from its recorded inputs. The report counts outcomes by the state shown.
- **binding-v1 in one place** (`src/outcome`), replayed from vector o1: ASCII origins under the Appendix G grammar, the checkout ref hash over the id before its first `?` (an empty part gives `differs`), the one-order rule (`bound_elsewhere`), integer-only inputs (`parseIntegerJson` reads `1.0` as a non-number), and `ship_to_optional` false for every source until S1 answers for Shop.
- **Cap room comes back only on local evidence (contract §6).** An approval stops counting against the spend caps only when its latest `local` outcome is `failed` read from Shop, or `failed` by the gateway's own precheck with no `complete_checkout` disclosure for the purchase in the log. An outcome Intent Cloud reported, verified or not, never frees room: what a compromised Intent Cloud reported must not widen spending.

## Consequences

The gateway says what Intent Cloud reported, and what its own checks support, and never more: a forged or contradictory statement can lower what the gateway shows, never raise it. `intent verify` fails a chain whose shown outcome claims more than its statement. A status read now also verifies a signature, and the chain grows by one entry per distinct outcome. A host that serves outcomes without statements (any 1.5.0 host, or a broken 1.6.0 one) gets its outcomes recorded but not shown. Retention of completer keys still reads the status observation for a hand-off's terminal outcome (ADR-0016); moving it onto verified `outcome` entries is a follow-up. A `staging_webhook` source is accepted from any host while the gateway pins only the staging host; refusing it from a production host comes with the first production pin.
