# ADR-0023: Pause: stop every purchase through the gateway that is not paid yet

Status: accepted · 2026-10-18 · Relates to ADR-0014 (log before send to every destination), ADR-0019 (one-tap completion)

## Context

A developer who sees their agent misbehave needs one command that stops spending through intent at once, without waiting for a network round trip and without a passkey. Resuming must stay a human act, because a stopped agent that could resume itself would make the pause worthless.

The contract 1.7.0 draft adds `POST /v1/pause`. It is signed by the gateway session (Appendix C) like every other call, and its body is signed by an **account key**, an Ed25519 key that `intent init` makes on the developer's machine. The draft also says that while an account is paused, the submit, the `completing` outcome report and the confirm page's approval are answered `paused`. There is no resume route and no status route: resume is by passkey only, on the confirm page's `/account`. The 1.7.0 tree is not vendored yet.

## Decision

- **The local pause comes first.** `intent pause` (or the panel's Pause button) appends a `pause` entry `{from}` before anything is sent. From that entry on, the gateway refuses `create_cart` and the completion's `complete_checkout` before anything is built or sent. Each refusal is a `refused` entry `{step, reason: "paused", source: "gateway", purchase?}`, compare-and-appended under the store lease, so a resume chained meanwhile wins. The state is read from the chain alone (`src/pause`), so every process on the data dir honours a pause written by another.
- **The pause is signed and its counter only grows.** The account key signs UTF-8 `"intent-pause-v1\n"` followed by the JCS of `{account_key_thumbprint, counter, issued_at, action: "pause"}`; `action` is signed but not sent. The body is exactly `{account_key_thumbprint, counter, issued_at, signature}`. The next counter is one more than every counter the chain ever sent (read from the logged request bytes, so a send cut short by a crash still counts) or learned from a 409 `counter_replayed` (`last_counter`). It persists in the chain and strictly grows across restarts. `intent verify` fails a pause counter that does not grow.
- **One adapter holds the wire shape.** `src/contract/pause.ts` holds the path, the schemas, the error codes and the signed bytes, so they can be checked against the 1.7.0 tree once it is vendored. The call is sent with `Intent-Contract-Version: 1.7.0`.
- **The send goes through the disclosure log.** The pause request is a `disclosure` like every call to Intent Cloud (log before send, invariant 2), and its receipt is verified. Each send ends in a `pause_sent` entry `{pause_seq, counter, disclosure_seq, result, reason, …}`. Its result is `acknowledged` only for a 200 whose receipt verified; `failed` for a 400 `bad_request` or a 401, which are not retried; otherwise `retrying`. A 409 `counter_replayed` carries on at once from `last_counter + 1`. A 404 (the key is pinned only at the first passkey approval), a 429 (Retry-After honoured), a 400 `clock_skew` or no connection keep the local pause and retry.
- **A retry runs while `intent serve` runs.** It reads the chain every 5 s and sends again with backoff (5 s, doubling to 5 min, or Retry-After when longer) until Intent Cloud acknowledges. A pause written by the CLI or the panel is picked up the same way. `intent log`, `intent status` and the panel say when it is retrying.
- **Resume needs the passkey.** The gateway sends no resume of its own. `intent resume` prints the confirm page's `/account` address (from the latest verified key statement's confirm origin). It clears the local pause with a `resume` entry `{confirmed: false, pending: "next submit"}` only after the developer types `resumed` at a terminal. The next submit (`create_cart`) records a `resume_check` entry: `confirmed` when it is not answered `paused`, `repaused` when it is, which pauses again here. A submit answered `paused` with no pause recorded (paused from another device) appends a `pause` from `intent_cloud`.
- **Answers of `paused` are refusals.** A cart, approval or outcome report answered `paused` is a `refused` entry with `source: "intent_cloud"` naming its disclosure. A `completing` report answered `paused` is not a refusal of the purchase for good: it is sent again later.
- **The panel's only write.** With `intent panel`, the page shows a Pause button. It sends `POST /pause` carrying this run's random token in the `x-intent-panel-token` header. The panel accepts it only from its own Origin, and not from a cross-site fetch (`Sec-Fetch-Site`), on `127.0.0.1` only. A custom header cannot be sent cross-origin without a CORS preflight the panel never answers, and no GET has a side effect.
- **The honest line.** Every place that offers the pause says: "`intent pause` stops every purchase that goes through intent and isn't paid yet. For a hard stop, also turn off the budget in the Shop app."

## Consequences

- A pause holds on this machine at once, whatever the network does, and stops a purchase at its next outward step; a `complete_checkout` that may already have left is reconciled, never sent again.
- It is not a hard stop. An agent with a shell can read the Shop token and pay Shop directly, which no gateway rule can see. The Shop app's budget switch is the hard stop, and the docs say so.
- The account key is readable by anything running as the developer, the agent included, like the Shop token. A stolen account key can only pause; resume needs the passkey.
- Until a build carries the account key, a machine has none: the pause holds locally only, and `intent log` and `intent status` say "no account key on this machine".
- The chain gains five entry kinds: `pause`, `pause_sent`, `resume`, `resume_check` and `refused`. A gateway from before this change refuses a chain that holds one, as with any new kind. `intent verify` checks their order: a resume only while paused, a `resume_check` only for the unconfirmed resume in effect, a gateway refusal only while paused, a `pause_sent` only after its pause, naming its own disclosure's counter.
