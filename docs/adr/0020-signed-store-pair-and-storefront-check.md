# ADR-0020: Contract 1.6.1: the signed store pair, and the store pair check against the storefront

Status: accepted · 2026-10-18 · Amends ADR-0016 (contract version), ADR-0019 (where Shop's store comes from); relates to ADR-0014 (log before send to every destination)

## Context

Shop names a store by its `*.myshopify.com` domain; an offer, and the confirm page, name the storefront the buyer sees (S1). Until now the gateway gave one tap only to a store whose storefront is itself a myshopify host (ADR-0019), because the public contract carried no pairing of the two names.

Contract 1.6.1 (`SHA256SUMS` sha256 `bc035ee3…10d8`) adds the pairing. A Shopify merchant's `myshopify_domain` is on the offer, the cart and a new snapshot v3, so the passkey signs the pair (`merchant_origin`, `myshopify_domain`) and binding check 1 for `shop_agent` accepts either name of that one merchant. 1.6.0 is frozen (`b75b771e…657d`) and still answered to callers that name it. 1.6.1 is answered only on an explicit `Intent-Contract-Version: 1.6.1`, and an approval is read and reported on only in the version that created it (R8).

The passkey signs the pair but cannot judge it: the buyer sees only the storefront. Intent Cloud alone asserts that the two names belong together. So 1.6.1 makes the completer verify the pair against the storefront itself before it pays (Appendix G "Store pair check"). For the gateway that means a new outside destination: the merchant's own storefront.

## Decision

- **The gateway speaks 1.6.1.** It vendors the 1.6.1 tree byte for byte and sends `Intent-Contract-Version: 1.6.1` on every request. It refuses a host whose `Meta` names another version or sums hash, and an answer served in another version. Each `approval_pending` entry's `sent` now names `contract_version: "1.6.1"`.
- **Appendix E step 7 for 1.6.1.** A 1.6.1 `sent` takes only a v3 snapshot (refusal `v`), and its `myshopify_domain` must equal the offer's and the cart's, or be absent from all three. A `sent` with no version was chained by a 1.6.0 gateway: it takes only v2, so `intent verify` still checks those chains. Before any approval is requested, the gateway also refuses a cart whose `myshopify_domain` differs from the offer's, or that lacks it when the offer names one.
- **The store comes from the signed snapshot.** The D7 seam (`storeFor`, `myshopifyStore`) is gone. The Shop store a one-tap purchase uses is the v3 snapshot's `myshopify_domain`, and nothing else. A cart offers `shop_agent` only when the offer names a valid myshopify domain and a wallet is linked. An approval without a signed domain is refused before anything is sent (`store_unknown`).
- **Binding check 1 reads the store Shop reports.** The observed merchant origin of a Shop checkout is `https://<store>`, or the merchant origin Shop reports when the checkout lives at the signed store. binding-v1 matches it against either signed name (`src/outcome`, vector o1's seven new cases). Any other store differs.
- **The store pair check, before the `completing` report.** After the budget checks and before `create_checkout`, the gateway sends `GET <merchant_origin>/meta.json` and passes only when the answer's `myshopify_domain`, ASCII only and lowercased, is exactly the signed domain. The rules are the contract's: https only; no IP literal, `localhost`, single-label or numeric-last-label host; 5 s in total; at most 64 KiB, counted on the bytes read; status 200 only, so a 3xx is a failure and is never followed; `application/json`, parameters allowed; a JSON object with no duplicate member names and no BOM. The pure rules live in `src/contract` (`metaUrl`, `storePairProblem`) and replay all 49 cases of vector o5. A failure here is local: `failed` / `gateway_precheck`, reason `store_pair:<rule>`. No Shop checkout is made and nothing is reported, so the approval is left `approved` at Intent Cloud and the buyer can still hand off.
- **The safety net at `complete_checkout`.** Right before the completer precheck, the pair must still pass, from a pass kept under 24 h or from a new GET. If it does not, nothing is sent, and `failed` / `gateway_precheck` is reported after the accepted `completing`.
- **The fetcher refuses non-public addresses and DNS rebinding.** `src/storefront` resolves the name once and refuses it unless every address is public: no loopback, private, link-local, CGNAT, documentation, multicast or reserved range, and IPv4-mapped and NAT64/6to4 forms included. It connects to the address it checked, with TLS verified for the host name, through a one-request agent, so Node never dials the name itself. The request carries a fixed header set (`host`, `accept`, `user-agent`, `connection`): no cookie, credential, `Authorization` or buyer data.
- **The storefront is a destination like any other (ADR-0014).** The GET goes through the disclosure core as destination `storefront`. Its `disclosure` entry (the URL, the fixed headers, no body, and the local `purchase`) is appended before the request leaves, and a failed append means no GET. The answer is kept as a `response` entry (status, sha256, size), never its content. Only `src/disclosure` may use `src/storefront`, and only tests and demo mode may load `src/storefront-fake`. The module rules and their fixtures enforce both.
- **The cache is the chain.** Each verdict is a `store_pair` entry: `{handle, merchant_origin, myshopify_domain, result, reason?, disclosure_seq?, cached_from?}`. A pass that names its GET (`disclosure_seq`) is reused for at most 24 h from that GET, keyed by (origin, domain), by any process on the data dir. A reuse is chained for the purchase with `cached_from` and is never reused in turn. A failure is never reused, so a failure cannot poison a later check. A pass chained with a timestamp after the current time (a clock that went back) is not trusted.
- **`intent verify` checks it.** A pass must name a storefront GET of that origin's `/meta.json` answered 200, or a fetched pass for the same pair under 24 h old. A failure must name a rule of the check. A `completion` for a v3 snapshot that signs a myshopify domain must come after a pass for this purchase and that pair. Evidence packs carry the purchase's `store_pair` entries, the pass they reuse and each GET with its response.
- **The rest of 1.6.1.** `shop_api` has `ship_to_optional = false` (already the gateway's value). Shop's checkout ref hash covers `gid://shopify/Checkout/<token>` without `?key=` (already the construction). A 14-digit `gid://shopify/Order/<n>` is a valid order reference (o2's second valid statement). An Intent Cloud outcome never names `shop_api` or `gateway_precheck` (schema). `outcome` and `outcome_statement` come together (`dependentRequired`). The R5 re-run of a gateway report on a v3 snapshot, as Intent Cloud returns it, is `incomplete`, every check it cannot observe `unknown` (option (a)); the gateway records it as Intent Cloud's report, never as a verdict. Shop does not deduplicate `create_checkout`, and the gateway already never sends it twice for a purchase.

## Consequences

- One tap can reach any Shopify store whose pair the offer names, as Intent Cloud returns it, not only stores whose storefront is their myshopify domain. A wrong pair in what Intent Cloud returns, by mistake or because it is compromised, gets no payment: the storefront has to name the same store.
- The merchant's storefront sees the developer's IP address before a one-tap purchase, once per pair and day while the check passes (a failure is never reused, so each later purchase asks again), with a fixed user agent and nothing about the buyer. A hand-off purchase never makes this request.
- What the check proves is that the storefront at the signed origin names the signed myshopify domain at the time of the GET. It does not prove who runs the storefront, and an attacker who controls the storefront origin's DNS or TLS controls the answer, as they would control the checkout.
- 1.6.0 approvals still open when the gateway moves to 1.6.1 are no longer readable by it (R8: 404). They expire within 15 minutes; the buyer starts a new cart.
- The chain gains one entry kind, `store_pair`. A gateway from before this change refuses a chain that holds one, as with any new kind.
