# Glossary

One entry per term: what it is, and its boundary. Vocabulary here is used as-is in code, docs and PRs. Record a new term in the same PR that introduces it.

| Term | Code name | What it is |
|---|---|---|
| **Gateway** | `intent-gateway` | The self-hosted gateway a developer runs with npx or Docker. It talks to the agent over MCP and to Intent Cloud for offers and carts. |
| **Intent Cloud** | — | The hosted service behind the gateway: product discovery, merchants, offers and carts. Reached only through its public API host. |
| **Gateway policy** | `policy.yaml` | The developer's YAML rules for what may leave the gateway and how much may be spent. It can only narrow Intent Cloud's rules, never loosen them. |
| **Cloud baseline** | `CLOUD_BASELINE` | The rules Intent Cloud enforces, held by the gateway as the loosest policy it will run: passkey approval, at most 3 items, US delivery, the excluded categories, both completion modes. Every policy is checked against it. |
| **Policy library** | `intent policy add` | The public, signed collection of shared gateway policies, reviewed by PR. |
| **Policy lock** | `policy.lock` | The file beside `policy.yaml` that `intent policy add` writes: the library policy's name, the commit it came from, its sha256, its source (`bundled` with the gateway, or `github` for `--commit`) and `policy_sha256`, the hash of the `policy.yaml` it wrote. It records what was applied, not the policy itself; a lock whose `policy_sha256` does not match `policy.yaml` is stale. |
| **Shopping session** | session key | A short-lived key for one anonymous run of searches and carts. The gateway sends no identifier that links it to other sessions. Not an account. |
| **Session keyid** | `gw-…`, `src/signing` | The shopping session's identity on the wire: `gw-` plus the base64url of its raw Ed25519 public key. Self-certifying: Intent Cloud reads the public key from it, with no registration. Every request carries it in its RFC 9421 signature (contract appendix C). |
| **Completer key** | `completer_keyid`, `<data>/completer/<keyid>.key`, `openCompleterKeys` | A fresh Ed25519 key the gateway makes for one cart (contract 1.6.0, ADR-0016). Its keyid goes in the cart request and in the snapshot the buyer approves, so under the contract (Appendix G R1, R7) it may sign reads and outcome reports of that one approval. Saved 0600 before the cart request leaves, used after a restart in place of the session key, deleted when the purchase no longer needs it. Only its keyid is ever sent or logged. Not a session key: it links no purchases. |
| **Contract version header** | `Intent-Contract-Version` | The request header naming the contract version the caller speaks. The gateway sends `1.6.0` on every request; a request without it is answered as 1.5.0. The response carries the version answered, which must be the gateway's own. |
| **Disclosure log** | — | The gateway's local hash chain of every field it sent to any outside destination (Intent Cloud, or a linked wallet for example), appended before each send: exact bytes, except credentials, which are kept only as their sha256 (ADR-0014). |
| **Destination** | `destination` in a disclosure, `DestinationTransport` | Where a logged request went: `intent_cloud`, or a wallet destination such as `shop` or `shop_accounts`. A disclosure without `destination` went to Intent Cloud. Every destination goes through the one disclosure core (`src/disclosure`). |
| **Answered** | `answered` delivery, `call` action | What `intent log` and the panel say of a request to a wallet destination that a response entry follows: the destination answered with the recorded status. Never "acknowledged" or "receipt": a wallet signs none. A `call` is one such request in the log's actions. |
| **Response entry** | `response` | The follow-up to a request to a destination that signs no receipt (a wallet): `{disclosure_seq, status, body_sha256, bytes}`, a digest and size of what came back, never its content. Not a receipt: nothing checks the answer itself. |
| **Redacted credential** | `[redacted sha256:<hex>]`, `redacted: [{at, sha256}]` | A credential in a logged request of a wallet request (an `authorization`, `proxy-authorization`, `cookie` or `x-api-key` header, a body value under a secret key such as `refresh_token`, `accessToken`, `password`, an OAuth `code` or any key whose last word is `token` or `bearer` (`session_token`), in a JSON or form body, or a path the destination declares secret), replaced in the log by the sha256 of the value sent. `intent verify` fails on a credential in clear ("holds a credential") and on a `redacted[].at` that names no such marker. |
| **Disclosure receipt** | — | Intent Cloud's signed statement of what it received, matched against the disclosure log. |
| **Disclosed cloud** | `createDisclosedCloud`, `connectCloud` | The only way gateway code reaches Intent Cloud: each call's outbound body is checked for buyer identity, logged with its exact bytes and headers, then sent, and what came back is logged. |
| **Unacknowledged send** | `unacknowledged` | A logged send with no HTTP response, or a non-2xx response with neither `Intent-Contract-Version` nor a receipt. `intent verify` reports it and does not fail (ADR-0006). When no connection was made at all (DNS failure, connection refused), its reason starts `CloudNetworkError: not sent`, and `intent log` and `intent verify` report the request as logged but not sent. |
| **No answer recorded** | `unanswered` (verify count) | A logged send with no follow-up entry: the gateway stopped before it recorded an answer, or is still waiting for one. `intent verify` reports it as "logged, maybe sent, no answer recorded" and does not fail while it is the last send of its gateway session; it is never counted as sent or acknowledged. |
| **Gateway session** | `session` entry `{id}`, `session: {id, n, open}` in a disclosure | One start of the gateway's disclosure log: a random local id in a `session` entry, carried by each disclosure with its number `n` and the numbers still `open` (awaiting a follow-up). Never sent. Not the shopping session. |
| **Discarded response** | `discarded` | A response that should have carried a valid receipt and did not: a 2xx (whose content the gateway never uses), any response with `Intent-Contract-Version`, or any invalid receipt. `intent verify` fails on it (ADR-0006). |
| **Local audit trail** | — | The same local hash chain read as a whole: disclosure log entries plus each signed Approval the gateway verified. |
| **Action** | `buildActivity`, `src/activity`, `intent log --json` | The local hash chain's entries grouped by what the gateway did: a search, a cart (with its approval request and link), an approval-status check, an approval, a block, a start, a key read, a pin or a flag. Each carries the requests it sent, what came back for each in `intent verify`'s categories (acknowledged, unacknowledged, not sent, maybe sent, discarded), its observation when one is recorded, and its outcome (`rejected` or `expired` for a status check whose observation says so). `intent log -v` and `--json` print actions; the panel can read the same model. A presentation of the chain, not an integrity check. |
| **Observation** | `observed` entry, `src/observation` | The gateway's local summary of what Intent Cloud returned for one request with a verified receipt (the body is not covered by the receipt): a search's offer count, how many the policy hid and up to 10 offers (handle, title, merchant, price, shipping); a cart's title, merchant, quantity and total (with its completion mode, merchant origin and estimated flag from contract 1.6.0); an approval's handle and state (with the outcome as served, before any check: its state, source, assurance, the order it names and the binding result it states, when the status has one). Appended after the receipt and naming the request by `disclosure_seq`. Never sent and not a disclosure; it never answers a request. Built with buyer identity withheld (`[withheld]`); `intent verify` checks its shape and reference. |
| **Fenced lease** | `audit.lock` | The expiring lock a writer of the local hash chain holds while it appends. Before each write the writer checks it still holds the lease and that the chain's tail has not moved; if either fails, that writer is refused for good. Liveness comes only from the expiry, never from a process id: a lease left by a gateway killed mid-write is taken over once it expires, and a command kept waiting on it says so after a second. |
| **Approval** | — | A buyer's passkey signature over one purchase snapshot, returned signed by Intent Cloud, verified by the gateway and appended to the local audit trail. One per purchase. |
| **Approver pin** | `approver_pin` | The passkey credential the gateway trusts for Approvals: the first one it verified, or one accepted later with `intent approver accept` at a terminal. Any other credential is flagged (ADR-0011). |
| **Approver fingerprint** | `approverFingerprint` | How a person compares passkeys: the SHA-256 of the canonical JSON of the passkey's public key (JWK), as 16 groups of 4 hex characters. The `approver_pin` and `approver_flag` entries carry it, the panel and stderr show it, and `intent approver accept` asks for it. |
| **Key statement** | `verifyStatement` | Intent Cloud's statement, signed by an offline root key pinned per host, listing its current and next receipt and approval keys. Valid 90 to 180 days (ADR-0006). |
| **Fake Cloud** | `startFakeCloud`, `src/cloud-fake` | A stand-in for Intent Cloud on 127.0.0.1 that follows the public contract and signs with its published test keys (vectors s1, d1, e1). Only tests and demo mode use it; it ships in the package for demo mode only. |
| **Soft passkey** | `SoftPasskey` | A passkey held in memory (ES256 or RS256) that answers the confirm page's WebAuthn request in tests and on the demo confirm page, in place of the buyer's authenticator. |
| **Demo mode** | `intent demo`, `startDemo`, `src/demo` | The gateway against the Fake Cloud in-process, with the sample catalog and the published test keys, so a developer can try the whole flow with no setup. Its chain lives in `<data>/demo`, starts with a `session` entry `{mode: "demo"}` and never mixes with a real one. Every tool result carries "DEMO: test keys, sample catalog, nothing can be bought." |
| **Sample catalog** | `SAMPLE_CATALOG`, `searchCatalog` | Demo mode's catalog: about seventy US offers from `*.example` merchants across everyday categories, searched forgivingly (case, plurals, synonyms, any category level, sizes within 20%). Its items in excluded categories are never returned. A search that finds nothing gets the line "The demo catalog has: …" in demo mode. The tests' Fake Cloud defaults to the smaller `DEFAULT_CATALOG`. |
| **Test root key** | `TEST_ROOT_KEY` | The `cloud-root-1` key of vector s1, whose private seed is public. Demo mode trusts only it; no Intent Cloud host may ever pin it. |
| **Demo confirm page** | `startConfirmPage` | The local page at `http://127.0.0.1:8788/confirm/c/<link>` (port 8788 unless `INTENT_DEMO_CONFIRM_PORT` names another, or it is taken) that shows a demo purchase snapshot with "Approve with demo passkey" and "Reject". A click signs with the demo's soft passkey, kept per demo data dir. It is a local stand-in for the passkey step: any program that can reach 127.0.0.1 can press it. |
| **Demo code** | `Demo.code`, `<data>/demo/approval-code` | Six digits, new on every demo start, that Approve on the demo confirm page needs. Printed on the gateway's stderr and kept in a 0600 file, never in a tool result, so an agent that reads only tool results cannot approve. A speed bump, not proof of a person. |
| **Invocation** | `INTENT`, `invocation()` | The command that runs this gateway, printed before every command the gateway suggests: `npx -y <spec>`, `node /abs/dist/main.js`, `intent`, or `docker exec <container> intent`. |
| **Readiness check** | `MissingDetail` | Before a search, the gateway checks it has a product or category, a budget and a 5-digit US ZIP. It lists the missing ones for the agent to ask the user about, never guesses one, and sends nothing until all are there. |
| **Spend history** | `spendHistory` | The purchases the policy's daily and weekly caps count, read from the local hash chain: every verified approval, plus every approval still pending and unexpired, so carts opened in parallel cannot add up past a cap. An approval stops counting only on local evidence that it charged nothing (`chargedNothing`); an outcome Intent Cloud states never frees room (ADR-0015). |
| **Outcome** | `outcome` entry, `src/outcome`, `OutcomeEntry` | What happened to a purchase after its approval (contract 1.6.0, Appendix G; ADR-0015): `handed_off`, `completing`, `ordered`, `mismatch`, `failed`, `checkout_expired`, `indeterminate` or `reported`, with the source that told it and its assurance (`verified` or `reported`). The `outcome` entry records either Intent Cloud's report (`basis: "cloud"`: its words, whether its statement verified, the gateway's binding re-run and the state shown) or the gateway's own verdict (`basis: "local"`). The state shown is never more than the verified statement (rule O1). |
| **Outcome statement** | `outcome_statement`, `verifyOutcomeStatement` | Intent Cloud's signed statement of an outcome: its approval key's Ed25519 signature over `intent-outcome-v1\n` and the canonical JSON of the statement. Valid for an approval only when it names that approval and the snapshot the passkey approved, and its outcome is consistent (amendment M2); a refusal names its rule (`refused_by`). The gateway acts on nothing else (M1). |
| **Binding check** | `binding-v1`, `bindingV1` | The five checks of an observed order against the approved snapshot: merchant origin, checkout ref hash, the one line (variant and quantity), ZIP and total (`ceil(0.8·A) ≤ R ≤ A`, USD). Each is `match`, `differs` or `unknown`; the result is `ok`, `mismatch` or `incomplete`. Inputs are read under the integer-only profile (`parseIntegerJson`), so `1.0` is never the integer 1. |
| **Disclosure summary** | `Sent: … / Blocked: …` | The last line of every tool result: the field names each request sent to Intent Cloud and whether a verified receipt acknowledged it, then what was held back. Names only, never values. |
| **Buyer identity** | `findIdentity` | Anything that identifies or pays as the buyer: name, postal address, card number, email, phone. The gateway refuses to send it; a ZIP code alone is not buyer identity. |
| **Hand-off** | `continue_url` | The step where the buyer leaves our confirm page for the merchant's checkout and pays there. The gateway never sees the buyer's name, address or payment. |
| **Completion mode** | `completion`, `CompletionMode`, `completion_accepts`, `completion_mode` | How an approved purchase is completed: `handoff` (the buyer pays at the merchant's checkout) or `one_tap` (a wallet adapter in the gateway completes it with the developer's own wallet account, see One-tap completion). In the contract, `one_tap` is `shop_agent`. The gateway policy's `completion` list narrows which modes a purchase may use; absent means both, and a cart that names no mode is a hand-off. A cart request offers the modes the policy allows and the gateway can complete (`completion_accepts`); the cart, and the snapshot the buyer approves, name the one Intent Cloud chose (`completion_mode`), which the gateway checks before asking for any approval. |
| **One-tap completion** | `completion`, `complete_attempt` entries, `advanceCompletion`, `appendUnless` | How the gateway completes a verified `shop_agent` approval with the linked wallet, inside `get_approval_status` (ADR-0018): a `completion` entry (the redemption: checkout ref hash, report id, idempotency key) and a `complete_attempt` entry (an owner token held in memory only), each compare-and-appended so one exists per approval, then the completer precheck and one `complete_checkout`, whose own disclosure is compare-and-appended. A possibly-sent purchase is only reconciled (`get_checkout`), never sent again; open or unreadable is `indeterminate`. |
| **Checkout vault** | `<data>/wallet/<rail>-checkouts/`, `openCheckoutVault`, `CheckoutIdStore` | The wallet's raw checkout ids, each sealed under the wallet key in its own file named by the checkout ref hash (ADR-0018), so a restarted gateway can read a checkout it may have completed. A raw checkout id is never in the chain. |
| **Verify command** | `intent verify` | Checks the local hash chain, matches receipts to the log, re-verifies approvals, and self-checks the npm package or image. |
| **Evidence pack** | `intent evidence`, `src/evidence`, `intent verify --evidence` | One purchase's slice of the local hash chain as one canonical JSON file (format v1, ADR-0018): the entries of that purchase whole (the requests sent, their receipts, the pending entry with `sent`, the approval proof, outcome statements and binding results, the key statements and approver pin they need), the `{seq, prev, hash}` of every chain entry, and the pinned root key. Anyone can check it offline. It holds no buyer identity and no credential in clear, and says what was sent and what was signed or acknowledged, nothing about what happened afterwards. Not the whole log: other purchases appear only as hashes. |
| **Doctor** | `intent doctor` | Checks the setup one line at a time (data dir, active policy and lock, chain and lease, root key, Intent Cloud's contract and key statement) and names the fix for each problem. Its requests go through the disclosure log. |
| **Default policy** | `DEFAULT_POLICY` | The bundled library policy the gateway runs when no `policy.yaml` exists, in every mode: `zip-only`, so the only buyer detail a search sends is a 5-digit ZIP. `strict-default` (no ship-to, so no search) stays available through `intent policy add strict-default`. Every command that uses the default says so. |
| **Canonical JSON** | `jcs` | RFC 8785 JSON restricted to safe integers (no fractions, no NaN, no lone surrogates): the exact bytes the gateway hashes and verifies signatures over. |
| **Data directory** | `Config.dataDir` | Where the gateway keeps its state: `INTENT_DATA_DIR`, else `/data` in the image, else the platform's per-user data folder. Resolved only by `src/config`. |
| **Root key pin** | `PINNED_HOSTS` | The root public key (kid `cloud-root-1`) the gateway trusts for one Intent Cloud host. It holds only that key; everything else trusted comes from the statement the key signs. `--trust-keys` replaces it for an unpinned host. |
| **Self-check** | `label: "self-check"` | A provenance or signature check of the gateway's own npm package or image, run by the installed gateway code itself. A tampered install could tamper with it too, so it always names the outside checks (`npm audit signatures`, `cosign verify`) that settle the question. On a build that was never published (no `build-info.json`, or the registry has no such name@version) it reports "not run" and does not fail `intent verify`; `--skip-install-check` skips it offline and says so. |
| **Gateway bundle** | `scripts/bundle.ts`, `dist/` | The gateway's code and its runtime dependencies compiled by esbuild into `dist/` (ADR-0013): `dist/main.js` (the Node check only), `dist/cli/index.js` and `dist/chunks/`, beside `dist/THIRD_PARTY_LICENSES` and `dist/sbom.cdx.json`. Not a Sigstore bundle (a signature with its verification material) and not a bundled library policy (one shipped in `policies/`). |
| **Release identity** | `releaseIdentity(version)` | The Sigstore certificate identity of a release: `https://github.com/golden007eye/intent-gateway/.github/workflows/release.yml@refs/tags/v<version>`, issued by GitHub's OIDC provider. npm provenance, the image signature and the SBOM attestation must all carry it (`docs/release.md`). |
| **Panel** | `startPanel` | The read-only local web page on `127.0.0.1`, in six views: Overview, Purchases (the purchase timeline), Approvals (with the approver pin fingerprint and flags), Policy, Server log (the whole chain, field by field) and Verify (the chain checks of `intent verify`). GET only; it never writes the chain and loads nothing from outside the gateway. |
| **Purchase** | `buildPurchases`, `src/activity` | One cart action read with what belongs to it: the search before it, the agent's approval-status checks and the verified Approval for its approval handle. Its state (approved, waiting, expired, refused, or the cart request's delivery) says only what the chain holds. The panel shows each as four steps: Search, Cart, Your approval, Agent checked. |
| **Public contract** | `contract/` | The Intent Cloud public contract: the gateway API spec, its normative appendices and test vectors, published under Apache-2.0. The gateway vendors it byte for byte; `contract/SOURCE.md` names the version and the sha256 of `SHA256SUMS`. |
| **Test vector** | `contract/vectors/*.json` | An input with the exact output Intent Cloud computed for it. Both sides must reproduce it byte for byte; formats are shared this way, never by sharing code. |
| **Claims rule** | `scripts/claims.test.ts`, `docs/claims-allow.txt` | Invariant 5 as a test: every sentence in the README, the docs and the CLI's strings that names Intent Cloud as an actor uses a verb from a short, checkable list (receives, acknowledges, returns, signs, enforces, reported), or is allow-listed with a reason. |
| **Feature map** | `docs/feature-map.json` | The features the docs describe as working, each with the `intent` subcommand or test file that proves it. A `!!! planned` block names its feature in a `<!-- feature: <id> -->` line, and that id must not be in the map. |
| **Wallet adapter** | `WalletAdapter`, `src/wallet` | The developer's own payment rail (first: their Shop account) behind one port in our terms: account budget, create, complete and read a checkout, revoke. Every call it makes goes through the disclosure log, and it returns only projected values, never buyer identity. Not a merchant integration: those stay in Intent Cloud. |
| **Shop adapter** | `connectShop`, `src/wallet-shop`, fake `src/wallet-shop-fake` | The wallet adapter for the developer's own Shop account (ADR-0017): our own MCP 2026-07-28 client to Shop's MCP server (destination `shop`, five allow-listed tools) and its account server (destination `shop_accounts`: the device flow that links the account, and revocation). Reached only through `src/disclosure`. Needs `INTENT_SHOP_CLIENT_ID`: no Shop client is built in. |
| **Projection** | `projectAccount`, `projectCheckout`, `projectOrders` | The allow-list copy of a wallet's answer: only the named fields (budget left, checkout reference, status, lines, store domain, merchant origin, total, order id; from an order list, each order's reference, total, merchant origin and creation time), the ship-to ZIP only as `match`, `differs` or `unknown`, and an error only as a status, a code and a fixed label. Everything else, buyer identity included, is dropped before anything is returned. |
| **Saved-address id** | `savedAddressId` | The opaque id of an address the buyer saved in their wallet account (`gid://shopify/…/<digits>`). The only way the gateway chooses delivery: it never sends address fields, and when a wallet would need them the step fails with `AddressFieldsRequiredError`, nothing sent. |
| **Checkout reference** | `checkoutRef`, `checkout_ref` | `sha256:` and the hex SHA-256 of a wallet's checkout id: how the gateway names, returns and records a checkout. The id itself can carry a credential (`?key=`), so the adapter holds it in memory only and the log keeps it as a digest. |
| **Store domain** | `storeDomain` | How Shop names a store: its `*.myshopify.com` domain. Not the storefront origin an offer shows; the adapter records both and never compares them. |
| **Wallet vault** | `saveSecret`, `<data>/wallet/<rail>.enc` | The one file that keeps a wallet rail's token: AES-256-GCM, 0600, replaced in one step, any changed byte or a wrong key refused. Its key comes from `INTENT_WALLET_KEY_FILE` (refused inside the data dir), else `INTENT_WALLET_KEY` (with a warning: its value is visible to anyone who can read the process), else a generated 0600 `wallet-key` file in the per-user config folder, outside the data dir. Against malware running as the same user it is obfuscation, not protection. `intent wallet unlink` asks the wallet to revoke the token (a logged send; `revoked: true` only when the wallet answered HTTP 200), deletes the file whatever the answer, and chains a `wallet` entry, whose body `intent verify` requires to be exactly `{rail, action, revoked}` (a wallet check's, its own seven keys): the token never enters the chain. |
| **Wallet link** | `intent wallet link shop`, `linkShop`, `wallet {action: "linked"}` | Connecting the developer's own Shop account: Shop's OAuth device flow (RFC 8628) as the gateway's registered client (`INTENT_SHOP_CLIENT_ID`; without one nothing is sent), scope `openid personal_agent` (no email). Each request is logged before it leaves, the device code digested; the tokens come back only in answers (logged as a digest and a size) and go to the wallet vault. The user code and the page to approve on are printed, never sent. Linking again keeps the earlier link until the new sign-in succeeds, then unlinks it as `intent wallet unlink` does (revoke, delete, chain `unlinked` with `revoked` as Shop answered). `intent init` offers it at a terminal and skips it otherwise; purchases are handed off; one-tap is not yet wired to purchases. |
| **Wallet check** | `intent wallet check shop`, `checkOrders`, `wallet {action: "checked"}` | An on-demand comparison of the orders a linked wallet reports (Shop's `search_orders`, one logged request) with the purchases the chain names: an order no `outcome` entry names is **unmatched**. Each order is projected to its reference, total, merchant origin and time; the chain gets only `{rail, action: "checked", since, order_count, unmatched_count, unmatched_total_minor, complete}`. It says what the wallet reported, never how an unmatched order was placed. No background polling. |
